# Sparkle Connect Repository Audit
**Audit date:** 20 October 2026  
**Scope:** Repository structure, web authentication/state, Supabase integration, Android backend dependencies, and Render build configuration.  
**Limitations:** This is a source review. The web build has now passed in GitHub Actions, but the Android app has not been built here, the live Supabase project has not been queried, and deployed user sessions have not been tested. Findings below distinguish visible code behavior from anything requiring runtime verification.

## Priority 0: Authentication and account security

### 1. Web login is currently local-state authentication, not real email/password authentication
In `apps/web/src/context/SparkleContext.tsx`, `signIn` looks up an account in the browser's `state.accounts` collection and compares a locally stored password. `signUp` creates a local object and updates React state. Neither function calls Supabase Auth to create or authenticate a user. The Gmail flow accepts a typed email address and derives a display name; it does not perform Google OAuth.

**Impact:** A user can appear logged in without authenticating with a trusted identity provider. Accounts are browser-local rather than available reliably across devices.

### 2. Account and password-like data is persisted in localStorage
The web context serializes `state.accounts` to localStorage, and account objects include a `password` property. Seed data also contains sample accounts with a shared demonstration password.

**Impact:** This is not safe for production authentication. Passwords must never be stored in browser localStorage or compared as client-side plaintext. Demo credentials should not be treated as real accounts.

### 3. UI copy overstates backend guarantees
The web auth modal says “Database Synced (Room / Local / Supabase)” and describes Gmail login as saving a profile to the database, while the visible sign-in/sign-up handlers mainly update local state.

**Impact:** The interface may tell users data has been saved or authenticated when the source code does not establish that.

## Priority 1: Shared backend and persistence

### 4. Android and web currently use different backend stacks
The Android Gradle configuration includes Firebase Auth and Firestore. The web application uses Supabase Auth/client and a Supabase PostgreSQL schema. No verified identity/data bridge between Firebase and Supabase was found in this source review.

**Impact:** Shared accounts, profiles, posts, and messages across Android and web cannot be assumed to work. Choose one source of truth or implement and verify a deliberate bridge before launch.

### 5. Web actions appear to update local React state rather than persist all mutations to Supabase
For example, the web `addPost` handler creates an ID and updates `state.posts`; the visible like/comment handlers also update local state. The realtime listener subscribes to database changes, but a subscription alone does not persist local changes.

**Impact:** Data may look updated in one browser while not reaching the cloud or other users.

### 6. RLS policy coverage needs a table-by-table review
The initial migration enables Row Level Security on many tables, but the visible policy section defines policies for only a subset. Tables without suitable policies can reject legitimate client requests; policies that are too broad can expose private data.

**Impact:** Verify each table's intended read/write access, including profile interests, follows, comments, likes, saved posts, attachments, community membership, events, reports, blocks, preferences, and security events. Do not solve access failures by exposing a service-role key to the client.

## Priority 2: Build and deployment quality

### 7. Render's React build command bypassed the project's TypeScript check
The package script is `"build": "tsc && vite build"`, but the Render Blueprint directly invoked Vite. That could publish a bundle without running the configured TypeScript check.

**Change made on this audit branch:** `render.yaml` now runs `npm install && npm run build` for the React SPA, so deployment follows the package build script.

### 8. Web build verification now passes
A GitHub Actions workflow was added at `.github/workflows/web-build.yml`. The workflow installs dependencies and runs `npm run build`, which executes `tsc && vite build`.

**Result:** The pull-request build completed successfully on 20 October 2026. This confirms the current web TypeScript check and Vite production build pass in CI. It does not confirm live authentication, database writes, Android builds, or end-to-end cross-device sync.

### 9. Two web deployments may cause confusion
The Render Blueprint defines both a root HTML static site and a separate React SPA. Confirm which URL is the canonical web app and ensure the root HTML version is not mistaken for the React/Supabase version.

## Recommended repair order

1. Replace simulated web login/signup/Gmail entry with actual Supabase Auth, create/read profiles by authenticated user ID, and remove client-side password storage and demo-password login from production paths.
2. Make Supabase the documented source of truth for web records, then ensure every feed/gig/community/event/message mutation persists and handles errors before updating the UI optimistically.
3. Decide whether Android will migrate to Supabase or use a deliberate Firebase-Supabase bridge; do not claim cross-platform sync until tested end to end.
4. Review and test RLS policies for every table using at least two normal users and an unauthenticated client.
5. Build the Android app and add automated Android checks; keep the web CI check on every relevant pull request.
6. Confirm one canonical production URL and update the README with the actual authentication and deployment behavior.

## Changes in this branch

- Updated the React SPA's Render build command to run `npm install && npm run build`, invoking TypeScript before Vite builds the production bundle.
- Added GitHub Actions CI for the web production build.
- The web CI build passed.
- No authentication, database schema, or Android source files were changed in this first pass, to avoid a risky backend rewrite without end-to-end testing.
